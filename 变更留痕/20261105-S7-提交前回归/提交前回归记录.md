## 1. 为什么要改这两个脚本

写 `sop/SOP-02-threeants-配置注入.md` §8 禁止事项第 9 条时写下
「禁止用 `sudo cmd < /proc/...` 形式读 root 进程文件」，随后独立复查发现
**仓库里有两个脚本正是这么写的** —— 文档与代码自相矛盾，提交前必须修一致。

| 脚本 | 原写法 | 问题 |
|---|---|---|
| `probe-threeants-config.sh` L52 | `CMD="$($SUDO tr '\0' ' ' < "/proc/$PID/cmdline")"` | 重定向由**当前 shell** 打开文件，`sudo` 对它无效。生产以非 root 的 `runyd` 登录时，若该文件不是世界可读就会**静默取空** |
| `probe-threeants-config.sh` L87 | `[ -d "$WD/config" ]` | 以当前用户判权限，而相邻两条 `find` 走 `$SUDO`。判据与实际读取能力不一致，会误报 `ABSENT` |
| `probe-utc-runtime.sh` L65 | 守卫 `[ -r "/proc/$MAIN_PID/cmdline" ]`，读取却走 `$SUDO` | 同上：若文件是 root-only，守卫会误判 `UNREADABLE`（假阴性） |

### ★ 更实质的问题：这些 0 计数是**否定性判据**

`has_additional_location` / `has_config_location` / `search_path_config_dir` 期望值都是「0 / ABSENT」，
而**「生产 threeants 无外置配置目录」这条结论正是建立在这些 0 上**
（它决定了 SOP-02 §1 里「不存在更轻的第三条路」）。

`CMD` 取空时这些计数同样会是 0 —— **「读到 0」与「真的没有」无法区分**，
正是 `README.md` §3 铁律 3「0 命中不可当否定结论」要防的形态。

所以修法不只是换写法，还要**显式暴露 CMD 是否真的读到了内容**：
新增 `proc_cmdline_len` 字段；`CMD` 为空时输出
`FATAL_EMPTY_CMDLINE（…下面所有 0 计数均不可采信）`。

## 8. 提交前门禁（同日执行）

### ★ 先记录一次「数字对不上」的追查 —— 查出审计工具的真实盲区

第一次跑门禁时得到 `扫描文件数=64`，而 `git diff --cached --name-only` 是 **66**。
差 2 个。这种数字对不上的情况**不能放过**，否则等于在残缺扫描面上采信 CLEAN。

追查到根因：`audit-tmp-creds.sh` 的 `find` 用的是**扩展名白名单**
（`*.sh *.json *.yml *.yaml *.properties *.conf *.env *.txt *.md`），
而 `.gitignore` 与 `.gitattributes` **没有匹配的扩展名 → 被静默跳过**。

这不是良性差异：这类无扩展名文件恰恰最容易被人顺手粘进 token，
而漏扫之后汇总照样打印 `CLEAN` —— 构成**「在残缺扫描面上给出干净结论」的假阴性**，
比直接报错更危险，也正是 `README.md` §3 铁律 3 要防的形态。

已做的两处修复：

1. **白名单补全**：加入 `.*ignore` / `.*attributes` / `Dockerfile*` / `Makefile*` /
   `*.service` / `*.cfg` / `*.ini` / `*.xml` / `*.http`，并显式 `-not -path '*/.git/*'`。
2. **让结论自带扫描面**：新增 `扫描面=已扫/总数` 输出；
   当两者不等时**不报 `CLEAN`，改报 `CLEAN_PARTIAL`** 并明写
   「在白名单补齐之前，不得把本结论当作全仓 CLEAN 使用」。

改完**重跑 selftest**（因为动了 `find`，必须确认正控夹具仍被匹配到，否则 selftest 会假通过）：


## 9. 追加 `.gitattributes` —— 行尾不能只靠本机配置保障

`git add -A` 时报了一批 `CRLF will be replaced by LF` 警告，只涉及 `.md` / `.txt`，
**18 个 `.sh` 不在其中**。进一步用 `git ls-files --eol -s` 核实：

```
100644 … 0  i/lf  w/lf  attr/   scripts/probe-utc-runtime.sh     ← attr/ 为空
（18 个 .sh 全部 i/lf w/lf attr/）
core.autocrlf = input
```

`.sh` 在 index 与工作区都是 LF，看起来没问题。但 **`attr/` 为空**说明
行尾正确**纯粹依赖本机的 `core.autocrlf=input`**，没有任何仓库级保障。

这是一个会在别人机器上炸的陷阱：换一台 `core.autocrlf=true` 的 Windows 机器检出，
`.sh` 会带 CRLF，scp 到 Linux 执行时报 `$'\r': command not found` 或
`bad interpreter: /bin/bash^M`，而且报错点往往落在脚本中段，很难一眼看出是行尾问题。
**本仓的全部用途就是把脚本送上生产**，所以这个必须钉死。

已加 `.gitattributes`（`* text=auto eol=lf`、`*.sh text eol=lf`、二进制标 `binary`），
并 `git add --renormalize .` 后复验：

```
100644 7ccec13… 0  i/lf  w/lf  attr/text eol=lf   scripts/analyze-error-delta.sh
全 index 内 i/crlf 或 i/mixed 命中数 = 0
```

`.sh` 的 blob 哈希（`7ccec13…`、`0c59870…`）在 renormalize 前后**未变** →
证明它们本来就是 LF，这次只是把保障从「本机配置」提升到「仓库强制」，没有改动内容。
