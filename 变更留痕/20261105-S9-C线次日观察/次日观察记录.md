### 2.3 ★ 日志是脉冲式的：一个我误判为「不可能」的数字

修订后的 `watch-cline.sh` 回归运行（18:13）给出的 `CardFlowQueryConsumer=117728`，
与 07 号取证 C 节（~18:07）用**完全不同的实现**（`cat` + awk 单遍 `index()`）得到的
`117728` **一字不差**。我当即判定「相隔 6 分钟、期间日志增长约 6900 行，两次相同不可能」，
理由是速率约 258 行/分钟。

**这个判定本身是错的。** 实测（18:15:07 / 18:15:52 / 18:16:21 三次）：

```
size=30862178 → 30862359    mtime=2026-11-05 18:16:00   ← 文件在写，日志源活着
grep -c CardFlowQueryConsumer = 117728（四次相同：18:07 / 18:13 / 18:15 / 18:16）
按小时总行数：  16: → 7029     17: → 7012     18: → 6937（18:16 时已接近整小时的量）
```

`18:` 这个小时在 **16 分钟内就写完了 6937 行**，而 `16:`、`17:` 两个**完整**小时也才
7029 / 7012 行 → **每小时约 99% 的量集中在 HH:00–HH:04 的爆发里，之后近乎静默**。
18:07 / 18:13 / 18:16 三次都落在静默段，计数不动完全正常。

**错在哪**：那个 258 行/分钟是 `117728 ÷ 1103 分钟` 的**平均值**，
而真实分布是脉冲式的。**用平均值去否定两次实测相等，是一个未经检验的假设。**

**两个正面结论**：

1. `watch-cline.sh` 的 `grep -c` 与 awk 单遍 `index()` 是**两套独立实现**，
   在同一数据上给出完全相同的计数 → **判据③ 的数字有交叉验证**，不是单点自证。
2. 日志的脉冲结构**正好解释了 §2.1 的窗口假象**：短窗口若错过 HH:00–HH:04
   与 00:30 / 01:20 / 02:20 / 13:20 / 14:20 这几个 xxl-job 分钟，看到的就是「几乎没有活动」。
   day0 的 28.7 分钟窗口撞上了 13:00–13:04（故 ⑥ 峰值全在这 5 分钟），
   却**错过了 13:20**（故 `CellSafetyClient` 只数到 5 条）。

→ **推论（对后续观察有约束力）**：任何短窗口观察都必须先说明它**覆盖了哪几个爆发分钟**，
否则计数低到 0 都无法区分「没发生」与「没覆盖到」。

## 4. 本轮新发现（均为原计划外）

### 4.1 ★ 观察口径本身的缺陷：`FlowAccountRemoveTerminalListener` 不可观测

源码 `utc-mall/src/main/java/com/ryd/utc/mall/listener/FlowAccountRemoveTerminalListener.java`：

```java
final Collection<Long> terminalIds = event.getTerminalIds();
if (terminalIds == null || terminalIds.isEmpty()) {
    return;                                   // ← 静默，无日志
}
final FlowAccount flowAccount = event.getSource();
if (flowAccount == null || flowAccount.getId() == null) {
    log.warn("[移除卡关联] 事件源或账户ID为空, 跳过");   // 有日志
    return;
}
final List<FlowPackage> packages = flowPackageService.findByFlowAccountId(flowAccount.getId());
if (packages == null || packages.isEmpty()) {
    return;                                   // ← 静默，无日志
}
```

**后果**：事件真的到达、监听器真的被调用，但只要账户当时没有流量包，
就**一行日志都不打**。于是 `count=0` 有两种互斥解释，**日志无法区分**：

1. 窗口内没有发生「退卡但账户仍有其他卡」的事件；
2. 发生了，但走了 `packages.isEmpty()` 静默分支。

→ `watch-cline.sh` 注释里「① 为 0 = 窗口内无真实事件」这句话，
**对这个类是错的**。这不是工具写错了，是**被观测的代码本身缺少可观测性**。

**修复建议（属 utc-server 源码仓，需经 Hub 走件）**：在两条静默 return 前各补一行
`log.info("[移除卡关联] 账户 {} 无流量包/无待退卡, 跳过", ...)`。
成本一行，收益是让「退卡清理是否被触发」永久可判定。
**注意这不是缺陷修复而是可观测性补强**，不得与业务变更混在一次提交里。

### 4.2 ★ `FlowAccountEvent` 计数是一个无意义的指标

`FlowAccountEvent` 是 `utc-common` 里的**接口**（含 `Cancel`/`AppendTerminal`/`RemoveTerminal` 三个静态内部类）。
事件的**发布**（`new FlowAccountEvent.Cancel(x).publish()`）本身不打日志；
接口名只会出现在**堆栈跟踪**里。

→ 06 号取证 A 表显示 `FAEvent` 在 7 个采样日**全为 0**，包括监听器确实触发了的 11-04。
**它永远为 0，恒为 0 的指标不提供任何信息，却会让人误以为「这一项也检查过了」。**

**修复建议**：把 `watch-cline.sh` 的 ① 列表里的 `FlowAccountEvent` 去掉，
或改为统计**发布方** `FlowAccountServiceImpl` 的类名（发布点在该类内，若加日志才可观测）。
当前应先删掉，避免制造虚假覆盖感。

### 4.6 ★ PII 全仓核查：三轮取证才得到正确答案

由 §4.5 引出——既然日志正文含 iccid / openId，就必须确认**本仓（已推送 GitHub）里有没有真实个人数据**。
第一次内联测量给出 `ICCID_20DIGIT=161`、`MSISDN_11DIGIT=57`，看着像严重外泄。**这个数字是假的。**

| 轮次 | 做法 | 结果 |
|---|---|---|
| 1 | 内联 `bash -c` + 单引号内含双引号 | `161 / 57`，并列出「命中文件分布」一长串 |
| 2 | 脚本文件 + 判定实验（`TOTAL/ANYDIG/D12/D18/D20/D20occ/PREV_INLINE`） | **`D20` 全 0**；且 `ANYDIG ≠ PREV_INLINE` → 连我「模式退化成了任意数字」的解释**也是错的** |
| 3 | 脚本文件 + **带前后边界**的判据 | **真 iccid `hits=2`、真手机号 `hits=0`** |

第 3 轮的正确判据与对照：

```
真 iccid：  (^|[^0-9])[0-9]{20}([^0-9]|$)          hits=2
真手机号：  (^|[^0-9])1[3-9][0-9]{9}([^0-9]|$)      hits=0
对照 无边界 [0-9]{20}                               occ=3
对照 无边界 1[3-9][0-9]{9}                          occ=56   ← 假手机号的来源
其中 >=21 位长数字串                                occ=1（出自 指纹台账.md）
其中 >=12 位长数字串                                occ=99
```

两个假阳性来源：

1. `[0-9]{20}` 会在 **sha256 十六进制串内部**命中。十六进制里 0-9 占 10/16，
   20 位连续数字段概率约 8.7e-5，但本仓有约 96 个指纹，实测确实出现了 1 处 ≥21 位。
2. `1[3-9][0-9]{9}` 会在 **12 位 `agentFlowId`（`1308…`）内部**命中。
   `agentflow-prod-query.txt` 上 lines=29 / occ=43，全是内部子串，**一个手机号都没有**。

那 2 处真 iccid 的语义分类（掩码后）：

```
D-#   D) 零写库：只调只读端点。所有 ICCID 入参一律用不存在的假卡号
DD:#      DDDDDDDDDDDDDDDDDDDD，命中 D 行 → 不产生 INSERT/UPDATE，
DD-#      也不会把真实卡数据打进终端或日志。
DD:FAKE_ICCID="DDDDDDDDDDDDDDDDDDDD"
```

→ 都在 `scripts/probe-utc-http.sh`（行 10 的注释与行 42 的赋值），变量名就叫 **`FAKE_ICCID`**，
是**我自己设计的不存在假卡号**，下游 **H01 / H04 / H05 / H06 / H09** 五个探针都用它
（`/openapi/terminal/detail`、`/openapi/flow/package/list` ×2、`/openapi/recharge/list`、`/openapi/iccid`）。
设计前提「命中 0 行」有独立证据：`../20261104-S3-utc-admin-换包/utc-http-after.txt` 里
**H01 / H04 / H09 全部 `code=0 OK datalen=arr:0`（空数组）且三者 sha256 完全相同**；
另 H05 = `code=-1 请求参数非法`（该探针本就测非法枚举，预期），H06 = `code=0 OK obj:2`（分页壳，`data.content`+`totalElements`）。

**定案：本仓无真实个人数据，无需 rewrite git history。**
`PII_FOUND` 属**形态匹配正确、语义判定为假阳性**——与凭据工具里 `HARDCODED` vs `QUOTED`/`VAR_REF`
是同一件事：**形状命中 ≠ 语义泄漏**。已登记台账 §9 第 25 / 26 条。

这证明「让结论自带它覆盖了多大范围」这个改动是有效的。

已补 11 个扩展名（`runlog/out/log/diff/patch/csv/tsv/sql/ps1/bat/toml`），重跑：

```
selftest：HARDCODED=2/2 QUOTED=2/2 VAR_REF=1/1 REDACTED=2/2 REGEX_FRAG=1/1 UNSCANNABLE=1/1 → SELFTEST_OK
全树：  扫描文件数=79  扫描面=79/79（未覆盖 0）  UNSCANNABLE=0  有效扫描面=78/79
        HARDCODED=0  VAR_REF=7  QUOTED=0  REDACTED=8  REGEX_FRAG=14  剔除自指文件=1  → CLEAN  AUDIT_EXIT=0
```

一般化结论（已写进脚本注释）：**白名单永远会漏**，所以分母必须独立统计（`TOTAL_FILES` 不套白名单），
且只要 `SCANNED != TOTAL` 就**不得**报 CLEAN。补白名单只是缩小差额，**不是消除机制**。
