## 1. 为什么需要这次验证（问题的由来）

生产 threeants 的 `application-prod.yml` 里，`utc.agent-flow-coefficient` 与
`utc.agent-flow-recharge-min` 两个键是**故意注释掉的**（fail-closed 设计，
CRP-20261022-01-R1 A12/B4），原意是杜绝误搬测试机的 50/0 造成校验口径漂移。

后果：`UtcProperties` 虽然已有 `Integer agentFlowCoefficient` / `Integer agentFlowRechargeMin`
两个字段（commit 713dfd3 加的），但运行期 getter 全为 `null`，
`AgentServiceImpl` 的预划拨分支 100% 抛「经销商流量池不存在」。

**这是现役缺陷，不是可选优化。** 生产 unit 的 `ExecMainStartTimestamp = 2026-10-28 01:12:59`，
截至 2026-11-05 已连续 8 天处于该状态。

修复通路是注入 `-D`。但注入前有一个**看不见的风险**：
若键名拼错或 profile 前缀不对，Spring Boot 对未知属性是**静默忽略**的 ——
服务照常启动、配置照旧为 null、缺陷照旧，而且**不产生任何异常**。
所以必须先把「键名到底绑定得上不上」这件事测出来。

## 2. 方法：负控制（negative control）

不去调 pre-transfer 接口（它要求 `context.getLevel()==0` 一级经销商 + JWT 鉴权，
为读一个配置值去构造业务凭据，代价与风险都不划算，且会产生业务数据）。

改为**故意注入一个无法转换成 Integer 的值** `NOT_A_NUMBER`：

| 情况 | 可观测结果 |
|---|---|
| 键名绑定得上 | 启动期抛绑定异常、异常里**点名该属性**、端口起不来 |
| 键名写错/没绑定 | 全程无异常、端口正常起来 |

两种结果都可判定，不需要任何业务凭据、不产生任何业务数据。
用「必然失败」当信号，比用「必然成功」当信号更硬。

**已得出的三条结论：**

1. **两个键名都确实绑定得上**（neg / neg2 各自独立证明一个键，互为独立验证）。

## 4. `-D` 位置规则的一处纠正（此前写错过，已修）

我曾把规则写成「JDK 8 下 `-jar` 之后的 `-D` 会失效」并写进了仓库文件。**这是错的**，
被生产 cmdline 直接推翻 —— 生产现役 ExecStart 是：

```
/bin/sh -c "exec /usr/bin/java -jar -Xmx256m -Xms256m -Dspring.profiles.active=prod \
  -Dserver.port=7003 -Dfinance-refund.enabled=true \
  /usr/local/ryd-unicard/bin/unicard-official-1.0.0.jar \
  > /usr/local/ryd-unicard/var/official.log 2>&1"
```

`-jar` 在**最前面**，三个 `-D` 全在它之后，而 `spring.profiles.active=prod` 确实生效。

正确规则：**`-D` 必须在 jar 文件名之前**，与 `-jar` 标志本身的位置无关。
HotSpot 启动器是按「遇到第一个非选项参数才当作 jar 文件名」来解析的；
真正致命的是把 `-D` 放到 jar 文件名之后（那里开始全是程序参数）。
neg3 就是专门用来把这条**测出来**而不是靠传闻。

## 5. jar 同源性验证 —— 测试机结论能否外推到生产

这是外推的前提。若不成立，前面全部结果都只是「A 的证据」，不能给 B 背书。

### 5.1 触发点

| | sha256 | bytes | mtime |
|---|---|---|---|
| 生产 | `bd24267b…2b05` | 93,135,977 | 2026-10-28 00:58:20 |
| 测试机 | `56fcc758…afba` | 93,135,977 | 2026-10-24 23:48:03 |

**字节数完全相同但整包 sha256 不同** → 整包哈希在此**没有判别力**。
（ZIP 逐条目时间戳不同、而时间戳字段定宽，故同源两次构建总尺寸不变但整包哈希必变。）

### 5.2 第一次尝试失败（且失败得有价值）

`compare-jar-class.sh` 直接比 `UtcProperties.class` 的 sha256，得 `matched_entries = 0`。
脚本的 **0 命中 FATAL 守卫正确拦住了**「两边都 0 命中 → 哈希相同 → 误判成同一个 jar」的假阳性。
原因：`UtcProperties` 在嵌套的 `BOOT-INF/lib/unicard-*.jar` 里，fat jar 外层 `unzip -l` 看不到。

### 5.3 改用全清单递归比对

方法：`unzip -v` 提取每个条目的 `(长度, CRC-32, 条目名)`，`LC_ALL=C sort` 后整体算 sha256。
时间戳不参与，故同源两次构建应得相同哈希；任何代码差异都会暴露且能定位到具体条目。

**外层清单（291 条目）比对结果 —— 只有 3 条不同，且长度全部一致：**

| 条目 | 长度（两边相同） | 测试机 CRC | 生产 CRC |
|---|---|---|---|
| `META-INF/maven/com.cnc.unicard/unicard-official/pom.properties` | 128 | `4fdae8c0` | `5d800626` |
| `BOOT-INF/lib/unicard-common-1.0.0.jar` | 236204 | `96e50ea0` | `9d36cd9e` |
| `BOOT-INF/lib/unicard-data-1.0.0.jar` | 298184 | `3b656742` | `c19f2258` |

**全部 40 个 `BOOT-INF/classes/` 条目（长度 + CRC）逐条一致。**

清单判别力已单独验证（`inspect-jar-manifest.sh`）：291 条目 = 185 个 `BOOT-INF/lib/`
+ 40 个 `BOOT-INF/classes/` + 7 个 `META-INF/` + 21 个目录条目，
且含 2 个自有模块 jar。若 `BOOT-INF/lib/` 为 0 或无自有模块 jar，脚本会报
`MANIFEST_NO_POWER` 并拒绝下结论（这种「清单相同但覆盖不到关心对象」是比空清单更隐蔽的假阳性）。

**递归下钻到嵌套 jar 的内层清单：**

| 层级 | 条目数 | 不同条目数 | 差异条目 | 剔掉 `#` 注释行后的归一化 sha256（两边） |
|---|---|---|---|---|
| fat jar 外层 | 291 | 3 | official/pom.properties + 2 个嵌套 jar | `11acff69…25c0` ✅ 相同 |
| `unicard-common` 内层 | 225 | 1 | common/pom.properties | `b906ab41…9a8f` ✅ 相同 |
| `unicard-data` 内层 | 158 | 1 | data/pom.properties | `5b7d7cb8…6455` ✅ 相同 |

**三个关键类逐字节相同（长度 / CRC-32，两台机器一致）：**

| class | 长度 | CRC-32 | 意义 |
|---|---|---|---|
| `com/cnc/unicard/common/config/UtcProperties.class` | 6407 | `c5d879b3` | **绑定 `-D` 键的那个类** |
| `com/cnc/unicard/data/service/impl/AgentServiceImpl.class` | 50853 | `32a73066` | fail-closed 抛出点 |
| `com/cnc/unicard/common/service/AgentService.class` | 4125 | `0f5683a1` | 接口 |

### 5.4 结论

**生产与测试机跑的是同一份代码。** 每一层唯一不同的条目都是 Maven 的 `pom.properties`，
而剔掉 `#` 注释行后的归一化哈希两边完全一致 —— 即差异**只在**构建时间戳注释，与代码无关。

因此：键名绑定行为与 `-D` 位置规则属编译期/启动器行为，同码必同结果，
**neg / neg2 / neg3 的结论可直接外推到生产，无须在生产上故意制造启动失败**。

> 方法论备注：这个结论**没有**靠「同尺寸所以大概同源」这种形态推断得出。
> 「等长 + CRC 变」确实符合两次构建的特征，但那只是推断；
> 真正的证据是内层清单逐条比对 + 归一化哈希 + 关键类的 (长度, CRC) 直接对照。

## 6. 生产环境移植性探测（只读，`生产移植性探测.txt`）

把测试机脚本搬到生产前逐条实测，结果发现**两个会导致静默假阴性的坑**：

| 项 | 生产实测值 | 影响 |
|---|---|---|
| `systemd_version` | **219**（CentOS 7） | `systemctl show -p KEY --value` **不支持**（报 `unrecognized option`），`NRestarts` 属性**不存在**，`StartLimitIntervalUSec` 在 219 里叫 `StartLimitInterval` |
| journal | **空** | ExecStart 是 `/bin/sh -c "exec java … > official.log 2>&1"`，重定向在 sh **内部**完成，systemd 收不到任何输出 |
| `/proc/13930/cmdline` | `-r--r--r-- root root`，`read_len_nosudo=170`=`read_len_sudo=170` | 世界可读，重定向写法在生产**其实能工作**（我原先的担心不成立，但已实测证明而非假设） |
| `has_agent_flow_D` | **0** | 生产 cmdline 里没有任何 `-Dutc.agent-flow-*` → **fail-closed 状态的运行期直接证据** |
| `Restart` / `RestartUSec` / `StartLimitBurst` / `StartLimitInterval` | `always` / `100ms` / `5` / `10000000`(=10s) | 见下 |
| `MainPID` / `ExecMainStartTimestamp` | `13930` / `2026-10-28 01:12:59` | 未被本轮只读操作影响 |
| unit 文件 | sha256 `ad1acd4d…570d`、1321 B、mtime `2026-10-28 01:12:15`、owner root | 与 S6 时完全一致 |

### 6.1 journal 为空 → 会造成本脚本最危险的假阳性

只读 journal 时 `KEYCNT` 恒为 0，于是 pos 模式会把「日志源是死的」当成「没有绑定异常」
→ 报出 **假阳性 POS_OK**。测试机上 journal 有输出，恰好掩盖了这一点。

已做的三处加固（`verify-d-injection.sh`）：

1. 支持 `TA_LOG` 指定应用日志文件；
2. **重启前记录该文件的字节偏移，重启后只读新增部分**
   （`official.log` 实测已 522 MB 且仍在涨，整读不可接受）；
   并处理观测期内被轮转/截断（`cur < off`）的情形 —— 此时 `tail -c +N` 会输出空，
   同样会退化成假阳性，故显式警告并退回整读；
3. 统计实际读到的日志行数与 Spring Boot 启动特征串命中数，
   **行数为 0 就在所有判定分支之前直接拦住并报 `LOG_SOURCE_DEAD`**（exit 7）。
   这道总闸不只保护 pos：neg 会误报 `NEG_KEY_NOT_BOUND`、neg3 会误报 `NEG3_OK`，
   都是「静默失效伪装成验证通过」。

### 6.2 注入错值后的失败形态 —— **无法断言，如实说明**

`Restart=always` + `RestartUSec=100ms` + `StartLimitBurst=5` + `StartLimitInterval=10s`。
单轮「启动 → 绑定失败」需数秒（测试机完整启动实测 16 秒），因此：

- 若单轮 < 2s → 10 秒窗口内 5 次启动 → 撞限流 → 单元钉在 `failed`，`restart` 被拒；
- 若单轮 ≥ 10s → 窗口内只有 1 次启动 → **永远撞不上** → 无限重启循环。

**我不能断言是哪一种**（要断言就得在生产上真的注入错值，而那正是要避免的）。
两种结果都是服务持续 DOWN 等人工干预，所以脚本在 `restart` 前一律先
`systemctl reset-failed`（幂等，单元没进 failed 时是无害空操作）。

这也再次支持 §5.4 的结论：**生产上不跑 neg 类模式**，只跑 pos。

## 8. 生产 / 测试机的结构差异（回归时新发现，影响修复方案选型）

| 维度 | 测试机 | 生产 |
|---|---|---|
| profile 传法 | `--spring.profiles.active=dev`（**程序参数**） | `-Dspring.profiles.active=prod`（**系统属性**） |
| 端口传法 | `--server.port=7003`（程序参数） | `-Dserver.port=7003`（系统属性） |
| 外部配置目录 | `--spring.config.additional-location=file:./etc/` **有** | **无**（S6 后 `candidate_yml_list=` 为空） |
| jar 路径 | 相对 `bin/unicard-official-1.0.0.jar`（靠 `WorkingDirectory` 解析） | 绝对 `/usr/local/ryd-unicard/bin/…` |
| `-X` 与 `-jar` 顺序 | `-X` 在 `-jar` 前 | `-jar` 在最前 |
| 输出去向 | journal | 重定向到 `official.log` |
| JDK | `/data/utc-unicard-test/jdk/jdk1.8.0_202/bin/java` | `/usr/bin/java` |
| Restart 策略 | `on-failure` / 10s | `always` / 100ms |

**对结论的影响**：Spring Boot 属性优先级中，Java 系统属性（`-D`）高于
jar 内/外的 application yml，但**低于命令行程序参数**（`--x=y`）。
生产用的是 `-D` 传 profile、且**没有任何外部配置目录**，
所以注入的 `-Dutc.agent-flow-*` 不会被任何 yml 覆盖 —— 通路成立。
测试机虽然有 `./etc/` 外部目录，但它也低于系统属性，故 neg/pos 的结论同样有效。

**但要注意**：生产没有外部配置目录这一点，意味着「不改 unit、只放一个外部 yml」
这条更轻的路子在生产上**当前不存在**，要用就得同时改 unit 加
`--spring.config.additional-location` 并新建配置文件 —— 比纯 `-D` 改动面更大。

## 10. 待用户裁定（本次验证到此为止，生产未做任何写操作）

生产 threeants 预划拨 fail-closed 已坏 8 天，修复通路已验证可用，但**修复方案有两条路，
且都需要重启生产 threeants（约 16 秒端口不可用）**，须用户选择并授权：

- **方案 A：注入 `-D` 到 systemd unit**（改 `/etc/systemd/system/ryd-unicard-official.service` L16）
  - 优点：不需重新构建；可逆（有备份 + restore）；本记录已完整验证通路。
  - 缺点：**产生配置漂移** —— jar 内 `application-prod.yml` 仍写着「已注释 / fail-closed」，
    而真实值躺在 unit 文件里。日后读 yml 的人会被误导。
- **方案 B：取消 `application-prod.yml` 里两行的注释、重新构建并换包**
  - 优点：符合 yml 注释里写明的原设计意图（「取数后取消注释填入」），单一事实源，无漂移。
  - 缺点：要构建 + 传输 + 替换 93 MB jar + 重启，改动面与耗时都大得多；
    且构建产物会带新的时间戳（不影响代码，但整包哈希会变）。

两条路都能修好缺陷。选哪条属于配置管理的架构决策，**我不单方面决定**。
