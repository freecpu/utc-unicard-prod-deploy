## 7. ★ 本次我的失误与顺带挖出的工具缺陷（如实记录）

> 7.1 / 7.2 是**我的失误**（一处纪律违反、一处不可逆的数据销毁）；
> 7.3 是一次被沙箱拦下后的正确处置；7.4 是归档环节暴露的**门禁工具缺陷**（已修）。

### 7.1 失误 A（严重）：取证时未脱敏，把生产 token 打进了终端输出

为确认「unit 文件能否归档进 git」，我执行了 `sudo cat -A <unit>` **整文件打印**。
该文件 L14 是 `Environment=OPENAPI_TOKEN=<64位十六进制>`，于是明文 token 出现在本轮终端输出里。

- 纪律是「凭据不入 git、不在正文复述」，我在**取证环节**就违反了它 —— 不是复述，是根本没先脱敏就去读。
- **补救与核实**：① 我在本记录与最终回复中均不复述其值；② 已核实 token **未进入 git** ——
  `变更留痕` 下三份 txt（01-preflight / 02-apply / 03-verify）只含 `grep '^ExecStart'` 的输出，
  不含 `Environment=` 行；全仓 `OPENAPI_TOKEN` 只作为**名字**出现 2 处（台账技术债第 6 条 + S3 记录），无值。
- **正确做法**（已写入台账 §5 的教训栏）：`sudo grep -v Environment= <unit>`，或
  `sudo sed 's/\(TOKEN=\).*/\1REDACTED/' <unit>`。
- 后果：该 token 本已在台账登记为「三处明文未轮换」（提醒 8 次未处理），现在又多了一处暴露面，轮换紧迫性上升。

### 7.2 失误 B：重启前没有备份 `official.log`，502 MB 生产日志被销毁

`ExecStart` 的重定向是 **`>`（截断）而非 `>>`（追加）**，所以**每次重启都会把 official.log 整份清零**。

```
log_offset_before = 526489119  →  重启后 7059  →  WARN: 在观测期内被轮转/截断，改为整读
```

- 销毁范围：2026-10-28 01:12:59 → 2026-11-05 17:25:12 的全部 threeants 生产日志（约 502 MB），**不可恢复**。
- 我的脚本**有「读」的守卫**（检测 `cur < off` 就警告并退回整读，避免退化成假阳性），
  却**没有「保」的动作**，也没在动手前向用户预警这一点。守卫救的是结论正确性，救不了数据。
- 影响评估：fail-closed 的结论链建立在 systemd 时间戳 + cmdline + jar 内 yml + 源码之上，**全部仍可复现**，
  故本次没有丢失定案证据；但那 8 天里业务侧真实报错的原始行**已无从查证**。
- `official.log.bak`（5.3 GB，9-28）**未受影响**。
- 已整改：SOP-02 §5 增加「重启前必须先 `sudo cp -p official.log <留档路径>`」的强制步骤；台账 §5 与 §9 第 2 条登记该机制。

### 7.4 ★ 归档后发现的第三个门禁盲区：PowerShell `Tee-Object` 写 UTF-16，门禁对它「空扫」却照样报 CLEAN

归档 4 份原始输出用的是 `ssh … | Tee-Object -FilePath …`。**Windows PowerShell 5.1 的
`Tee-Object` / `Out-File` 默认编码是 UTF-16LE + BOM**，于是：

| 观测 | 值 |
|---|---|
| `git ls-files --eol -s` | 4 份 txt 全是 `i/-text w/-text` → **git 判为二进制** |
| 全仓 UTF-16 BOM 扫描 | `UTF16_COUNT=4`（`TOTAL=72`），且**只有本轮这 4 份**；历史归档都是从 Linux scp 回来的 UTF-8 |
| 门禁当时的输出 | `扫描文件数=72`、`扫描面=72/72（未覆盖 0）`、`CLEAN` |

问题在于：UTF-16 里 ASCII 模式（如 `token=`）在字节层被 NUL 隔开，`grep -ohEi` **一条都匹配不到**。
文件被计入分母、也被计入「已扫」，实际是**空扫** —— 而汇总照样打印 `扫描面 72/72` + `CLEAN`。
这与本轮早些时候修的「扩展名白名单漏掉无扩展名文件」是**同一类缺陷的第二个实例**：
*在残缺的扫描面上给出干净结论*。上一次是「没进 find」，这一次是「进了 find 但读不出内容」。

处置：

1. **转码**：4 份 txt 读为 UTF-16 → CRLF 归一为 LF → 写 UTF-8 无 BOM。
   逐文件校验 `content_equal=True`；转后 `git ls-files --eol` 为 `i/lf w/lf attr/text eol=lf`，
   `file(1)` 判为 `UTF-8 text`，bash 侧 `grep -c .` 分别读到 28/66/38/6 行（转前读不到）。
2. **堵在工具里**（不能只靠人记住）：`audit-tmp-creds.sh` 新增
   - 扫描循环里用 `tr -d '\0' < f | cmp -s - f` 检测 NUL 字节（不依赖 `file(1)`，`tr`/`cmp` 到处都有），命中即计 `UNSCANNABLE` 并 `continue`；
   - 汇总新增机器可读行 `UNSCANNABLE=N` 与 `有效扫描面=已扫 − 编码不可扫 − 自指剔除`；
   - 结论分支新增：`NULN>0` → 报 **`CLEAN_PARTIAL`** 而非 `CLEAN`，并列出文件名与转码指引。
3. **给检测器配正控**（否则无法证明它会触发）：selftest 新增**正控 D** —— 同一条真明文
   `PASSWORD=fakePlainValue123` 写成含 NUL 的 UTF-16 字节形态（`iconv -t UTF-16`，
   失败则用 bash 逐字符插 `\000` 兜底）。要求同时满足：
   - `UNSCANNABLE=1`（检测器触发了）
   - `HARDCODED` 仍是 **2 而不是 3**（证明 grep 对 UTF-16 内容**真的**看不见）

   实测：`SELFTEST_OK`，`UNSCANNABLE=1/1`、`HARDCODED=2/2`。
   第二条才是这个夹具的价值 —— 它把「为什么必须有这道检测」变成了可执行的证明。
4. **重跑全树门禁**：`扫描文件数=72`、`UNSCANNABLE=0`、`扫描面=72/72`、`有效扫描面=71/72`、
   `HARDCODED=0`、`CLEAN`、`AUDIT_RC=0`。

> ★ 一般化教训（已超出本次任务）：**任何「扫描面 N/N 完整」的自证都必须回答
> 「这 N 个文件里，有几个是工具真的读出了内容的」**。「进了遍历」不等于「被检查」。
> 判据要覆盖到「读取是否成功」这一层，否则空扫会伪装成通过 —— 与 §3 里用
> `proc_cmdline_len=170` 给 `has_agent_flow_D=0` 做背书是完全同一个道理，
> 只是这次发生在工具侧而非探针侧。

> 附：本仓证据文件一律应为 **UTF-8（无 BOM）+ LF**。今后从 Windows 侧归档远程输出，
> 用 `ssh … > file` 重定向（PowerShell 5.1 下仍会是 UTF-16，需 `| Out-File -Encoding utf8`）
> 或直接 `scp` 远端产物，**不要**用裸 `Tee-Object`。
